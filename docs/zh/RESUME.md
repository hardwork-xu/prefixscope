## 四条有证据的项目描述

1. 实现基于请求入口 LRU 排名与前缀阈值直方图的 CPU 缓存容量分析器；在 Apple M1 Pro、Python 3.12.2 上，对公开 Qwen A/B 各前 2048 请求分析 64 个容量，五次重复中位耗时为 761.55/437.09 ms，独立有限 LRU 回放为 4314.70/2347.14 ms，加速 5.67×/5.37×。这是轨迹分析速度，不是模型推理速度。
2. 实现保持顺序的 Fenwick 时间戳压缩，排名槽位界为 `O(U + S0)`；在明确标为合成数据的 20,000 请求热点循环中，槽位从 524,288 降至 1,024。真实轨迹子集没有槽位缩减；进程 RSS 独立测量，不宣称同比例下降。
3. 使用独立 `OrderedDict` 基线，在 100 个随机种子和全部容量上建立精确正确性对照；覆盖冷启动、不足尾块、命名空间隔离、预算拒绝、压缩边界及清理重用，核心测试有 153 个通过用例。
4. 交付八种负载、360 次真实计时的完整原始证据，以及锁定依赖、双语 API/CLI 文档、wheel/源码构建、本地验收记录和 GitHub Actions 配置；明确区分已执行和未执行检查。

## 可准备的简短讲解

**为什么选这个问题：** 2026 年 9 月的 KVSET 论文让前缀工作集容量成为当周值得研究的话题。为多个预算重复回放同一历史浪费计算，但可信实现首先要定义“前缀命中”。

**核心如何工作：** 请求进入时每页有一个栈排名；前缀要驻留，所有页排名都必须小于等于容量，所以阈值是其中最大值。汇总阈值即可得到容量曲线。时间戳记录访问先后，压缩只重编号、不改变顺序。

**关键取舍：** 将“每容量回放一次”的工作转为“所有容量共享排名维护”。容量多时受益，单容量时明显慢于直接回放。压缩可节省长历史索引空间，但会有重建停顿，页大多为新页时没有空间收益。

**最重要的实验：** 两个预先指定的公开真实子集在 64 容量上超过 2× 分析目标，复用词元数精确一致；热点循环单独验证内存压缩。所有少容量退化及重复样本仍可查看。

**失败情况：** 前面某页缺失，后续即使驻留也不能算可复用前缀。新命名空间不能命中旧身份。预算超限在改变状态前拒绝；实际进程 OOM 则要求重建分析器。

**局限和后续问题：** 本模型省略输出 KV、引用固定及并发。事件适配器能否复现真实引擎的空闲队列转移？租户缓存池和动态容量应如何建模？能否在不隐藏额外状态的情况下降低压缩停顿？这些是后续研究问题，并非已完成功能。
