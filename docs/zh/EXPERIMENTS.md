## 冻结假设与判定

[实验前约定](../../experiments/contract.json) 已在实现与性能测量之前提交。主要问题是：需要评估多个缓存容量时，一次排名/直方图分析是否有价值。独立的工程假设是：对于长期重复访问小工作集的轨迹，时间戳压缩能限制数组存储。观察结果之后未修改原定目标。

| 测量前设定的目标 | 实测结果 | 判定 |
|---|---:|---|
| Qwen A 前2,048条请求、64容量，相比独立 OrderedDict LRU 的分析中位数至少加速2.00× | 5.6657× | 达标 |
| Qwen B 前2,048条请求，独立满足相同要求 | 5.3700× | 达标 |
| `hot_loop_20000` 上 compact/unbounded 已分配 Fenwick 槽位比≤0.25 | 1,024 / 524,288 = 0.001953125 | 达标 |
| 与独立有限容量 LRU 的复用 token 数精确相等 | 全部360个计时样本差值为零 | 在本实验中达标 |

这些是**分析程序**的结果，不是模型推理加速、生产缓存命中率预测，也不是优于 KVSET 的证据。数组边界是与进程 RSS 分开检验的工程性质；不能据此声称进程内存下降99.8%。

- Trace B：`68e3f98e2d601d60d0abf4b89bc8a3654372abab7b1cde6373a13d0054379d59`。

## 测量协议与公平性

每个工作负载分别评估1、8和64个容量。对于数量 `K`，容量为 `64 + 256*i` 页，其中 `i=0..K-1`；64容量范围因此为64–16,192页。三种方法使用相同的已归一化不可变请求列表、块大小、token 分母、容量网格及单线程设置：

- `lru`：每个容量维护独立 `OrderedDict` 缓存，直接检查前缀成员资格并更新最近访问顺序。这个实用的有限缓存算法同时提供精确参考答案，不使用排名或优化版本的直方图。
- `compact`：创建新分析器，使用可压缩 Fenwick 时间戳索引和聚合阈值直方图。
- `unbounded`：使用同一分析器，关闭时间戳压缩；时间轴数组按几何倍数增长。这保留其他分析逻辑，用于隔离压缩机制的影响。

每个负载/网格组合先为每种方法完整预热一次并丢弃计时结果，再分别测量五次。每次预热与重复都用已记录的种子打乱方法顺序。计时包含新分析器初始化、全部 observe、曲线构造及少量计数器提取；不含输入读取、身份归一化和参考答案验证。参考答案在计时外计算，每个计时输出之后以整数容量、复用 tokens 和总 tokens 字段进行比较。未关闭 Python 垃圾回收，也没有需要同步的 GPU 或异步设备计算。

**计时预热不等于缓存预热。** 每次预热和计分运行都创建空状态的新分析器，全部请求都计分；轨迹预热为零。没有人为把轨迹的第一个请求变成热请求。共保留360个计时样本、72个已丢弃但记录在案的预热样本，以及24个独立内存子进程测量；未删除任何有效计时样本。

输入读取与归一化单独计时，包括以有界缓冲区扫描完整源文件摘要，以及计算归一化请求摘要。A/B 2,048的这个阶段在本次运行分别耗时328.56/231.63 ms。这些是单次观察，包含证据哈希计算，不能当成流式解析器基准。分析加速比不含该阶段或 Python 启动，因此不能称作端到端加速比。整个 benchmark 的墙钟时间衡量实验运行成本，不是每条轨迹的端到端延迟。

生成表给出中位数和 compact 最小–最大值；原始 JSON 保留每次耗时和由中位数换算的请求吞吐。五次重复不足以支持 p99、可信的分布模型或跨机器结论。本次运行未绑定指定 CPU 核，也未控制频率/温度状态，机器没有与后台进程隔离。微小的时间差异不能证明具有统计意义的收益。波动不可忽略：64容量下 `mixed_chat_2048` 为239.65–685.46 ms，单容量下 `hot_loop_20000` 为915.95–2,466.53 ms。未过滤离群值。

## 实测速度与容量规划结果

| 主要64容量场景 | Compact 中位数（最小–最大），ms | 有限 LRU 中位数，ms | LRU / compact |
|---|---:|---:|---:|
| Qwen A，2,048请求 | 761.55（753.19–814.83） | 4,314.70 | 5.67× |
| Qwen B，2,048请求 | 437.09（391.49–528.24） | 2,347.14 | 5.37× |

两个预设主要目标均在本机和这些子集上达到。64容量时，分析器不会回放轨迹64遍或维护64个缓存，而是在一次 observe 遍历后用直方图回答容量扫描。**真实 Qwen 子集均未发生压缩。** 它们的加速支持多容量分析设计，不能证明压缩加速了这些真实输入。本项目没有与 KVSET 官方实现作性能比较。

![容量曲线](../../assets/capacity-curves.svg)

[容量图及双语说明](../../results/figures.zh.md) 展示用户实际需要的输出：页容量与 token 复用率的关系。64页时，A/B 2,048仅复用2.73%/1.04%的输入 tokens；320页时增至8.63%/25.97%；16,192页时达到23.34%/49.58%。因此，在这个采样区间内，B 的早期增益明显更大，在320和16,192页时高于 A；最初64页处则是 A 更高。不同请求组成和身份复用情况会改变曲线。所选子集不能证明整个数据集的命中率；缺少模型层数、头数和 dtype 信息时，也不能把页数换算成特定模型的 KV 字节数。

合成冷扫描在所有容量下复用率严格为零，尽管64容量的分析加速为16.82×。快速分析发现没有可复用前缀，是有效且有用的负结果，不是缓存性能提升。热点循环从64页时零复用增长至320页时97.11%；剩余未命中包含初始冷访问和不可复用的尾部 tokens。

## 压缩消融与实测内存

![分开的结构内存与进程内存统计](../../assets/memory.svg)

热点循环中，两种变体都对128个不同 ID 执行320,000次页访问。Compact 压缩356次，最终保留1,024个 Fenwick 槽位；unbounded 最终保留524,288个。比例为0.001953125，低于预设0.25。槽位数不含64位有符号数组未使用的下标0元素。字典、直方图、请求对象和临时分配均不包含在这个结构指标中。理论边界与摊销成本见[研究文档](RESEARCH.md#复杂度与资源成本)。

64容量的关闭压缩消融在热点循环上测得 compact 1,056.91 ms、unbounded 1,420.21 ms。这是有条件的运行时间收益，并非普遍加速：单容量热点循环中 compact 中位数更慢，为1,876.09 ms，对比1,787.44 ms，同时存在较大波动范围。

峰值 RSS 在64容量条件下为每个负载/方法另建一个进程，使用 `resource.getrusage(RUSAGE_SELF).ru_maxrss` 测量；macOS 字节和 Linux KiB 统一换算为字节。统计包含解释器、已加载的归一化请求、证据哈希、分析器及曲线。基线在该进程中同时保存所有要求的有限缓存。这不是硬件 KV 缓存分配、单独数组测量，也不是带误差条的重复估计。

| 场景 | Compact 峰值 RSS，MiB | Unbounded 峰值 RSS，MiB | 有限 LRU 峰值 RSS，MiB |
|---|---:|---:|---:|
| Qwen A 2,048 | 63.86 | 63.23 | 168.59 |
| Qwen B 2,048 | 44.50 | 42.94 | 131.62 |
| 热点循环20,000 | 46.88 | 48.61 | 47.11 |
| 混合 chat 2,048 | 33.83 | 30.20 | 96.52 |

热点循环的结构缩减很大，实测总 RSS 却仅相差约1.73 MiB。某些其他负载中 compact RSS 更高，例如混合 chat 的最终数组槽位虽减半，RSS 仍更高。输入、运行时分配和进程级波动都会影响结果。每个条件仅有一个 RSS 样本，证据支持报告这些观察与结构不变量，不支持声称已统计确认进程内存下降。

## 负结果、有效性与未验证范围

完整运行中的八个负载和全部正确性检查均通过；没有计时失败、超时或内存子进程失败。正确性通过不表示每个性能条件都有收益。**在所有测试负载上，1和8容量时 compact 均慢于有限 LRU。** 单容量 Qwen A/B 的 LRU/compact 仅为0.0525×/0.0405×，该条件下直接有限回放是实测更优的选择。冷扫描没有可复用 tokens；可压缩数组也无法让字典大小独立于不同页数量，冷流仍持续增长，直到声明的预算拒绝输入。

默认离线测试还覆盖非法/空数据、随机精确对照和资源拒绝，其执行状态以[验收记录](../../results/acceptance/checks.json)为准，不由速度基准替代。CI 配置和容器配方不能证明远端或 Docker 验证已经执行。本实验没有测量 GPU、Windows、模型推理、并发 vLLM/SGLang 行为、缓存 pinning、生成输出插入、TTL 或不同大小的缓存对象，也没有生产部署或模型质量评估。

后续主要研究问题包括：8与64容量之间的交叉点在哪里；更长或完整轨迹如何改变压缩活动和工作集增长；其他淘汰/pinning语义如何改变充分统计量的设计。后续实验需要另行记录条件与结果，本报告不外推这些结论。
